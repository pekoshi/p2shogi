# S18 KH の推論核: 追加入力を一時 buffer で足す

- 状態: 採用 / bit 一致: KH の on/off は評価値を変える (対象外)。 核の実装の検証は「エンジンと python の整数推論の一致」 / requires: M00
- 人間向け: `../SPEEDUPS_STORY.md` 8.1 節

## 1. 要約

浮き駒 (どの駒にも守られていない駒) の 78 次元の追加入力 (KH) を、 threat の accumulator と同じ 64 列に足す。 StateInfo の accumulator には書かず、 評価のときに「threat acc + KH の行」を一時 buffer に作って transform に渡す。 浮き駒が無い局面では buffer を作らない。 税 −0.34% [−0.93, +0.26] (64 周) で、 見積もり (−4〜−9%) より大幅に小さい。

## 2. 前提

- 差分更新される accumulator (threat) があり、 そこに「局面から毎回作る小さな追加入力」を足したい。
- 追加入力の発火は少ない (浮き駒は局面あたり数個)。

| 一般の言葉 | 本実装 |
|---|---|
| 追加入力 | KH の h 部 (浮き駒 78 次元)、 重み `kh.bin` (f32、 列優先、 64 列) |
| 足す先 | threat acc と同じ列 = FT の [0,32) と [512,544) |
| 実装 | `p2nnue_kh.h`、 `p2nnue_kh_fast.h`、 `p2nnue.cpp` の評価入口 |
| define | `-DP2_KH`、 option `KHFile` |

## 3. 不変条件

- 差分更新される accumulator (StateInfo) を書き換えない。 → LZ (S11) の物質化・差分と独立に保てる。
- 浮き駒の判定は局面だけで決まる (探索の履歴に依らない)。

## 4. 変更の最小単位

1. 局面から浮き駒の index の列を作る関数 (攻め駒の利きの bitboard の和と、 味方の利きの bitboard から)。
2. 評価の入口で、 列が空なら従来どおり threat acc をそのまま transform に渡す。 空でなければ 64 列の一時 buffer に threat acc を写し、 各 index の行を足して、 それを transform に渡す。
3. 照合: エンジンの静的評価と、 学習器側の整数推論 (python) が全局面で一致すること。 我々は KH の特徴を局面ごとに書き出す example (`kh_feat_dump`) とエンジンを照合した。
4. NPS: KH の重みあり / なし (同じ exe、 `KHFile` の有無) で M00。

## 5. bit 一致の検証

KH なし (`KHFile` 空) のとき従来と関門が一致すること。 KH ありは評価値が変わるので、 照合 (手順 3) で正しさを見る。

## 6. NPS の測り方と期待値

我々: `KHFile` あり / なしで −0.34% [−0.93, +0.26] (64 周、 PGO、 net khhr/a-4)。 `p2nnue_kh_fast.h` (浮き駒が無ければ buffer を作らない、 11-13) 単独の得は測っていない。

## 7. はまりどころ

- 見積もりは「行の加算が増える分」で −4〜−9% だったが、 発火が少なく一時 buffer も 64 列 (128 B) なので、 実費はほぼ 0 だった。 小さい追加入力は見積もりより実測。
- 追加入力を StateInfo の accumulator に混ぜると、 差分更新 (LZ) の不変条件が増えて壊れやすくなる。
