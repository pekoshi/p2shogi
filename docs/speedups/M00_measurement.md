# M00 測り方 (全仕様の前提)

- 種別: 方法 (高速化ではない) / 他の全仕様が参照する
- 人間向けの読み物: `../SPEEDUPS_STORY.md` 2 章

## 1. 要約

結果を変えない高速化は、 (a) 結果が本当に変わらないこと (bit 一致) と、 (b) NPS が本当に上がったこと、 の 2 つを別々に示して採用する。 (a) は探索結果の全一致の関門と、 新旧 2 経路の検算で。 (b) は CPU 時間の ABBA を 64 周以上で。

## 2. 前提

- 対象のエンジンが USI を話し、 `go nodes N` と `isready` を受けること。
- 同じ機械で、 他の重い処理 (対局・学習・ビルド) と重ならない時間に測れること。 重なる場合も CPU 時間なら比はおおむね保たれるが、 SMT の相方が埋まると核の cycle が 1.5 倍になることがある。 可能なら論理コアを固定し、 HT の相方を空ける。

## 3. bit 一致の関門 (結果が変わらないことの証拠)

```
for 局面 in 関門の局面集:
    isready                        # 置換表・history を消す (usinewgame は消さない実装がある)
    position sfen <局面> moves ... # 手順付きで送る (千日手の判定に要る)
    go nodes N                     # Threads=1
    最後の info 行と bestmove を記録: 手・nodes・depth・seldepth・score・pv
```

| 項目 | 我々の値 |
|---|---|
| 局面集 | G-a 49 局面 x 20 万ノード / G-b 150 局面 x 20 万 / G-c 24 局面 x 200 万 |
| 合格 | 全局面で手・nodes・depth・score・pv が完全一致 |
| 先にやること | 同じ exe どうし (base 対 base) で全一致することを確かめる (器自体が決定的か) |
| option | 本番で使う option をすべて渡す。 option を受け付けたか (`usi` の一覧に在るか、 範囲内か) を確かめる |

- 検出力の目安: 4% の局面にだけ出る崩れを 49 局面で捕まえる確率は 86%、 150 局面で 99.8%。
- `go nodes N` は Threads=1 でも実ノード数が N をわずかに超え、 停止の判定のタイミングで depth が揺れることがある。 局面ごとに `isready` を挟むと再現する。

## 4. 新旧 2 経路の検算

関門は探索の結果しか見ないので、 中間値 (accumulator・index・除算の商) を見る検算を別に回す。

```
#if defined(XXX_VERIFY)
    new_value = 新しい経路(…);
    old_value = 古い経路(…);       // 同じ exe の中で両方を計算
    if (new_value != old_value) { 1 件目を stderr に出して abort(); }
    ++n_checked;                  // 終了時に "XXX_VERIFY checked=… mismatch=0" を出す
#endif
```

- 既定 off の define にして、 本番ビルドには 1 命令も入れない。
- 5 局面 x 20 万ノード程度で十分な回数になる (我々の例: LZ IDXV2 で 457,217 対、 束 A で 14,779,636 回)。

## 5. NPS の A/B

```
腕 A (対照) と B (新) の exe を常駐させる
1 周 = 4 局面 x 100 万ノード を A B B A の順で (次の周は B A A B でも良い)
物差し = 各 go の間のエンジンプロセスの CPU 時間 (壁時計でなく)
周ごとに 比 r = CPU(A) / CPU(B) (同じノード数なので比 = NPS の比)
64 周 (足りなければ 128 周) の r の平均と 95% 区間 (t 分布) を出す
```

| 決めごと | 理由 |
|---|---|
| ABBA の交互 | 逐次実行は交絡する (−63% を −5.7% と読んだ例) |
| CPU 時間 | 壁時計は同居する処理で揺れる (実行順だけで +2.45%) |
| 64 周以上 | 8 周の半幅は ±3.6pt。 +1.6% を下限 > 0 で言うには 64 周以上 |
| PGO の有無を揃える | PGO は非 PGO の得の半分前後を先にやっている (LZ: 非 PGO +4.44% → PGO +2.25%) |
| 本番相当のビルドで | 計測用の define (rdtsc の probe など) を入れたビルドの得は、 本番ビルドに移らないことがある (+3.2pt → −0.2pt の例) |
| 判定線を先に書く | 例: 「CI 下限 > 100% かつ 点 >= +1.0%」。 結果を見てから線を変えない |
| 1 周目の数字を報告しない | 1 周目 +7.6% → 4 周で −1.4% の例 |

周回数の決め方: 半幅 ≈ 1.96 x sd / √周。 我々の器では 8 周の半幅 ±3.6pt から逆算して sd ≈ 4〜5pt/周 なので、 64 周で ±1.0〜1.2pt、 128 周で ±0.7〜0.9pt (実測の例: LZ の 128 周 [101.69, 102.87]、 段 1 の 64 周 [103.43, 105.01])。

## 6. はまりどころ

- **時間制の対局から取った NPS は A/B に使えない** (同じ exe が run ごとに +69% 揺れた)。
- **env スイッチや define がその exe に在るか**を確かめる (無いものを渡して「同じ条件どうし」を比べていた例)。
- **小さい正の改造を足し合わせると相殺する** (4 本で −1.52%)。 束は束で 1 回測る。
- **積和の回数 (MAC) では予測できない**。 測る。
- 対局の器: `go` の直後に `quit` を送ると探索が止まる。 `bestmove` を読んでから。
