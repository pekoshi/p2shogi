# S01 長い利きライブラリを外す (LE-off) + 1 手詰めを利きなし版に固定 (S02 を含む)

- 状態: 採用 / bit 一致: **適用前とは一致しない** (1 手詰めの判定が変わるため。 S02 と組で、 組の前後は「利きなし版どうし」で一致) / requires: M00
- 人間向け: `../SPEEDUPS_STORY.md` 4.1 節

## 1. 要約

do_move のたびに盤上の全利きを差分で更新するライブラリ (やねうら王の `LONG_EFFECT_LIBRARY`) を無効にし、 評価関数が要る利きは magic bitboard で局面から直接求める。 利きを毎手更新する費用が消える。 非 PGO で +8.88%、 PGO の採り直しと合わせた本番比で +3.91% (先読み pf4 込み)。

## 2. 前提

- エンジンが「毎手更新される利きの表」を持っていて、 それを使う機能が限られている (評価関数の特徴の作成、 1 手詰めの判定など)。
- その機能が、 利きの表の代わりに bitboard の利き (magic / 空盤の表) から同じ情報を出せる。

| 一般の言葉 | 本実装 |
|---|---|
| 利きの表のライブラリ | `LONG_EFFECT_LIBRARY` (やねうら王) |
| 1 手詰めの利きなし版 | `mate1ply_without_effect.cpp` (やねうら王に在る) |
| 1 手詰めの版の固定 | `-DP2_MATE1PLY_NOEFFECT` |
| 利きを使っていた評価の特徴 | threat の列挙、 MOB (閉じた実験) |

## 3. 不変条件

- 評価関数の値は、 利きの表から作っても bitboard から作っても同じ (特徴の定義が同じなら)。
- 1 手詰めの結果は版によって変わりうる (詰みを見つける範囲が違う)。 よって探索の木は適用前と変わる。 **ここだけは bit 一致を求めず、 「利きなし版に固定した後」を新しい基準にする**。

## 4. 変更の最小単位

1. ビルドの define から `LONG_EFFECT_LIBRARY` を外す。 → コンパイルエラーになる箇所が、 利きの表を使っていた箇所の一覧になる。
2. 評価関数の特徴で利きの表を参照していた箇所を、 magic bitboard (飛び駒) と空盤の利きの表 (歩み駒) に置き換える。
   - 中間検査: 適用前の exe と、 局面ごとの静的評価 (`eval` コマンド等) が全局面で一致すること。
3. 1 手詰めの判定を利きなし版に固定する (利きの表がある版と無い版が切り替わる作りなら、 無い版を選ぶ define を足す)。
   - 中間検査: 「利きの表あり + 1 手詰め利きなし版」と「利きの表なし + 1 手詰め利きなし版」で関門 (M00) が全一致。 これで「利きの表を外したこと」自体は結果を変えないと示せる。
4. PGO を採り直す (熱い経路が大きく変わるので、 古い profile は害になる。 S04)。

## 5. bit 一致の検証

手順 4 の 3 の形で、 「1 手詰めの版を揃えた上で」関門を通す。 我々の記録: 関門 24/24、 100 局面 x 20 万ノード完全一致、 PGO 版 60 局面 x 20 万完全一致。 1 手詰めの版の固定 (S02) 自体は探索木の一致 10/10 (固定前後で、 LE 版の判定を使わない設定どうし) で確認。

## 6. NPS の測り方と期待値

M00 の形。 我々の実測: 非 PGO 108.88% [106.70, 111.18] (6 周、 当時の器)。 PGO を採り直した本番比で、 do_move での FT 行の先読み (pf4、 後に LZ と相性が悪く外した) と合わせて +3.91% [+2.44, +5.62] (8 周)。 期待値は「利きの表をどれだけ頻繁に、 何に使っていたか」で大きく変わる。 やねうら王の既定のビルドはもともと `LONG_EFFECT_LIBRARY` を使わないので、 本家には関係ない。

期待値が出ないときに疑う順: ①define が本当に外れたか (前処理の結果を grep) ②PGO を採り直したか ③利きを使う別の経路 (詰み探索など) が残っていないか。

## 7. はまりどころ

- 1 手詰めの版が切り替わると探索の木が変わる。 「LE を外したら木が変わった = 外し方が誤り」と早合点しないこと。
- 非 PGO の得 (+8.88%) は PGO 後に 3 分の 1 強に縮んだ。
