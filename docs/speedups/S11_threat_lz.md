# S11 LZ: 大きな疎入力 (threat) の多段 lazy 差分更新

- 状態: 採用 / bit 一致: 一致 / requires: M00、 (推奨) S01
- 人間向け: `../SPEEDUPS_STORY.md` 5 章
- 後続: S12 (IDXV2)、 S13 (ROWPF)、 S16 (D1FAST)、 S25 (BACKMAT、 不採用)

## 1. 要約

評価のたびに全駒を走査して threat の accumulator を作り直していた (評価の 99.2%) のをやめ、 **評価する時点で**、 accumulator が有効な最寄りの祖先 (最大 8 手前) から 1 手ずつ差分を作って足す。 途中の祖先にも結果を書く (物質化) ので、 次の兄弟は 1 手の差分で済む。 PGO 128 周で 102.25% [101.69, 102.87]、 非 PGO 8 周で +4.95% [+3.70, +6.14]。

## 2. 前提

### 2.1 一般の言葉で

- 評価関数に「駒の対」の大きな疎入力がある: 攻め駒 X (玉以外) が標的 T (玉以外) に利いているとき、 対 (X の種類・色・位置、 T の種類・色・位置) に対応する行を accumulator に足す。 全計算は「全攻め駒 x その利き先の標的」。
- 対の index は、 視点 (先手 / 後手) と、 玉の位置による鏡像の有無で変わる。
- accumulator を持つ局面ごとの状態 (StateInfo) があり、 do_move で子の状態を作る。 子の accumulator は「無効」で始まる。
- 行は整数 (i8 / i16) で、 accumulator は i16 の wrapping 加算 (飽和しない)。 → 足し引きの順序に依らず値が決まる。
- (我々固有) 進行度の bucket を 4 つの群に分け、 群ごとに別の行の表を持つ。 群が違えば accumulator は別物。

| 一般の言葉 | 本実装 |
|---|---|
| 疎入力 | threat (profile 0、 216,720 次元、 出力 64 列 x 2 視点) |
| 全計算 | `ensure_threat_both` → `add_threat_dual` (`p2nnue.cpp`) |
| 多段の差分 | `lz::resolve` (`p2nnue_lz.h`) |
| 局面の状態 | `StateInfo` の `p2_threat_valid[2]`、 `p2_threat_group`、 threat acc |
| 群 | bucket → 群 [0,1,1,2,2,3,3,3] |
| 遡りの上限 | `P2_LZ_DMAX` (既定 8) |
| 1 手の対の上限 | `P2_LZ_STEPCAP` (既定 256 / 1 視点) |

### 2.2 1 手の差分の恒等式

駒 p が A → B に動き、 B にいた駒 c を取った (取らなければ c なし) とする。 P = 動く前、 C = 動いた後、 occ_min = occ(P) ∩ occ(C)。

```
Δ = − pairs_P(p が攻め駒として A から)  − pairs_P(c が攻め駒として B から)
    + pairs_C(p (成りなら成った駒) が攻め駒として B から)
    + Σ_{X ∈ Att} [ pairs_C(X) ∩ M(X) − pairs_P(X) ∩ M(X) ]
Att  = attackers_to(A, occ_min) ∪ attackers_to(B, occ_min) − {A, B}   (両色の攻め駒)
M(X) = 飛び駒: (attacks_P(X) ⊕ attacks_C(X)) ∪ {A, B}
       歩み駒: {A, B}
```

- 標的として A・B に立っていた / 立った対は、 Att の項の {A, B} の部分で入れ替わる。
- 飛び駒のレイの変化: 「レイ上の occupancy が変わった ⇔ occ_min で A か B に届く」なので `between_bb` は要らない。
- 打つ手は A なし (p は持駒から)、 取りなし。 null move は Δ = ∅。
- 我々の実装では 482,594 件の差分で全計算との不一致 0 を確かめた。

## 3. 不変条件

1. valid[c] が真 ⇒ その局面・視点 c・その局面の鏡像・**今の群**の accumulator である。
2. 差分の基点に採るのは、 **両視点 valid ∧ 群が一致 ∧ 基点の鏡像 (玉を巻き戻して判定) が今の鏡像と同じ** 祖先だけ。
3. do_move / null move は valid を落とし、 群を「なし」にするだけ (do_move では threat の計算をしない)。
4. 進行度 (bucket) を計算する node の集合を変えない (bucket は呼び出し元から受け取る。 新たに計算すると float の加算経路が変わって木が変わる)。
5. 行の適用は全計算と同じ関数 (順序非依存)。
6. 遡りの上限 DMAX、 1 手の対の上限を超えたら全計算に落ちる (値は変えず費用だけ抑える安全弁)。
7. 多重集合として ADD − SUB = pairs(C) − pairs(P)。 攻め駒・標的とも玉を含まない。
8. **物質化は valid な node に一切書かない** (下の 7 章の崩れの原因)。

## 4. 変更の最小単位

1. **全計算の valid 判定に群の一致を足す** (群を持たない構成なら不要)。
   - 中間検査: 関門 (M00) で従来と全一致。
2. **遡り**: 評価する node から祖先を DMAX 手まで辿り、 不変条件 2 を満たす祖先 P を探す。 途中の node (dirty の手) を列に積む。 見つからなければ全計算 (従来)。 null move の node は Δ=∅ として通過。
3. **盤の巻き戻し**: 今の局面の盤 (81 升の駒と、 種類別の bitboard) を作業用の写しに取り、 列の手を新しい方から 1 手ずつ undo して、 各手について 2.2 の Δ を作る (ADD / SUB の index の列)。 index は「視点ごと・鏡像込み」で 2 本ずつ作る。
4. **適用**: 基点の accumulator を写し、 古い方から各手の ADD を足し SUB を引く。 1 手ごとに、 その手の後の node の accumulator を書き (物質化)、 valid を立て、 群を書く。 ただし既に valid な node には書かない。
5. 失敗の経路 (鏡像が違う、 対の上限超え、 root に到達) は全部、 従来の全計算に落とす。
   - 中間検査 (必須): 検算 `LZ_VERIFY` を作る — 差分で作った直後に、 別の buffer へ全計算を作り、 両視点の全列を比べる。 不一致は 1 件目で abort。 5 局面 x 20 万ノードで不一致 0。
6. 関門 (M00) を広い形で (49 + 150 局面 x 20 万、 24 局面 x 200 万)。
7. PGO を採り直して NPS (M00) を 64〜128 周。

## 5. bit 一致の検証

- 検算 (手順 5): 我々は差分 482,594 件で不一致 0 (設計時の probe)、 IDXV2 の後の検算で 457,217 対で不一致 0。
- 関門: 223 局面 (G-a 49 x 20 万 / G-b 150 x 20 万 / G-c 24 x 200 万) で手・nodes・depth・score・pv が全一致。

## 6. NPS の測り方と期待値

| 条件 | 我々の値 |
|---|---|
| 非 PGO、 8 周 | 104.44% [102.69, 106.15] (別の測定で +4.95% [+3.70, +6.14]) |
| PGO、 8 周 | 101.62% [98.28, 105.53] — 区間が 0 をまたぐ (器の分解能不足で一度棄却した) |
| **PGO、 128 周** | **102.25% [101.69, 102.87]** |
| 本番の exe どうし (profile の鮮度の差を含む) | 104.18% [103.50, 104.85] (64 周) |

効きの内訳 (LZ 後、 計測ビルド、 中盤 5 局面): 差分の適用率 86.6%。 d=1 が評価の 75.3% (2,146 cycle = build 1,577 + apply 569)、 d=2 7.5% (3,606)、 d=3〜8 3.8% (7,067)、 全計算に落ちた 13.4% (4,575)。 差分 1 回が全計算の 0.47 倍かかるので、 節約は全計算比で 37% にとどまる。

期待値が出ないときに疑う順: ①適用率 (遡りが成功する割合。 計測ビルドで数える) ②全計算に落ちる理由の内訳 (祖先なし / 鏡像 / 対の上限 / root) ③d=1 の build の費用 (S12・S16 の的) ④行の待ち (S13 の的) ⑤PGO の採り直し。

## 7. はまりどころ

- **物質化が「valid だが群の違う」祖先を上書きして崩れた** (49 局面中 2 局面、 nodes +26 / +10)。 遡りは「valid ∧ 群一致」で止まるので、 valid だが群の違う node は素通りして列に積まれる。 そこへ今の群の accumulator を書くと、 その node が root の反復深化・aspiration の再探索・null move の verification で自分の bucket で再評価されたときに、 別の群の表の値を使う。 → 不変条件 8。
- この崩れは 4% の局面にしか出ない。 49 局面の関門は 86% しか捕まえない。 150 局面以上で。
- **書き込みをしない影の probe では崩れが再現しない**。 差分経路の検査は書き込みの副作用を含める。
- 全計算の経路で新たに bucket (進行度) を計算すると、 進行度を計算する node が増えて float の加算経路が変わり、 木が変わる (不変条件 4)。
- 7 月の Stockfish 式 (do_move で毎手差分を作って持つ) は −22.7%。 使われない差分を作らない「評価時に作る」形が肝。
- 10 月の「親が valid のときだけ差分」は親が valid な割合が 34.7% で効かなかった。 多段の遡りと物質化が要る。
- 2 本目の net (OPN) で本体を評価しない局面が続くと、 祖先が誰も threat を持たず全計算が増える (S25)。
