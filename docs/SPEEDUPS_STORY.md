# 高速化の記録 — threat の税を払いながら速くする

この文書は p2shogi のエンジン高速化を、 通して読める形でまとめたものです。 各節の終わりに、 実装仕様 (AI 向け、 `speedups/<id>.md`) へのリンクを置きました。 根拠にした実験記録 (設計書・判定ログ) は非公開です。 数字の出どころと書き方の約束は `OVERVIEW.md` 0 章、 全件の機械可読の一覧は `speedups/index.json` です。

機械はすべて Intel Core i7-7700 (Kaby Lake、 4C/8T、 AVX2 のみ、 L2 256 KB、 L3 8 MB)、 コンパイラは clang (llvm-mingw) です。 VNNI や AVX-512 のある CPU では結論が変わりうる箇所に印を付けました。

## 1. 出発点 — threat を足したら何が起きたか

threat 特徴は「どの駒がどの駒に利いているか」の対を入力にするもので、 216,720 次元あります。 評価のたびに、 玉以外の全駒 (平均 30.7 枚) を攻め駒として走査し、 利いている標的との対 (平均 61 本 = 2 視点) を作って、 その行を accumulator に足します。

最初の全幅版 (出力 1024 列) は NPS の税が大きく、 9 月に出力幅 K を掃引しました。

| K | 税 |
|---:|---:|
| 1024 | −37.5% |
| 512 | −32.0% |
| 256 | −24.8% |
| **64** | **−17%** (採用) |

行の幅が 64 列 (i8 で 64 B = 1 キャッシュライン) になり accumulator の費用はほぼ消えましたが、 **列挙の 13.6% は K に依らず残りました**。 その後の測定でも税は 19.4% → 26.6% (09-14、 静かな機械で) → threat を剥いだ net 比で 22〜30% (11-05) と出ています。 1 手 1 秒の対局で NPS の 2 倍は +70 Elo 前後 (対数則) とすると、 税 22% は 30 Elo ほどに当たります。

11-10 に評価 1 回の内訳を rdtsc で測りました (計測ビルド、 中盤 5 局面)。

| 部分 | cycle / 評価 | 割合 |
|---|---:|---:|
| accumulator (FT の差分更新 + threat) | 2,844 | 28% |
| forward (transform + fc0 + 後段) | 6,334 | 63% |
| heads ほか | 884 | 9% |
| 合計 | 10,062 | |


## 2. 測り方を先に直した話

この開発で最も多くの時間を失ったのは、 速くする工夫ではなく**測り方の誤り**でした。 今の測り方は次の形です。 各仕様の「NPS の測り方」の節はこれを前提にしています (`speedups/M00_measurement.md`)。

```
腕 A・B を同じ局面・同じノード数で交互に: A B B A A B B A ... (ABBA)
1 周 = 4 局面 x 100 万ノード x 2 腕、 これを 64 周 (約 25 分)。 足りなければ 128 周
物差し = 探索プロセスの CPU 時間 (壁時計でなく)
比 = 周ごとの CPU 時間の比の平均と 95% 区間
PGO の有無を揃える。 採用の判定は PGO 同士で
```

失敗から学んだ順に並べます。

1. **逐次実行は交絡する** (09-02)。 A を全部回してから B を回して、 −63% を −5.7% と読んだ。 → 交互に回す。
2. **壁時計は使えない**。 対局や学習と同居すると揺れる。 実行順だけで +2.45% 出た (09-28)。 → CPU 時間。
3. **8 周では +2% は見えない**。 8 周の半幅は ±3.6pt。 LZ は 8 周で区間が 0 をまたいで一度棄却し、 128 周で 102.25% [101.69, 102.87] と確定した (11-09)。 → 半幅は 1/√周 なので、 狙う効果量から周回数を先に決める。 1 周 23 秒なので 64 周は惜しまない。
4. **1 周目の数字は信じない**。 幅 512 の 1 周目 +7.6% → 4 周で −1.4%、 クラス順走査 +3.20% → −0.16% (11-05 に 3 回)。
5. **計測ビルドの改善は本番ビルドに移らない**。 診断用の define (`P2_DIAG` / probe) を入れたビルドで +3.2pt 出た「攻め駒をクラス順に走査する」改造は、 本番相当のビルドで −0.2pt だった。 計測ビルドは機構の切り分けにだけ使い、 採否は本番相当のビルド (できれば PGO) で決める。
6. **PGO は非 PGO の得の半分前後を先にやっている**。 LZ は非 PGO +4.44% → PGO +2.25%。 LE-off は +8.88% → +3.91%。
7. **積和の回数 (MAC) は NPS を予測しない**。 行を 44% 減らして +0.57%、 層を直列に足すと MAC +22% で −2.98%。
8. **bit 一致の関門は広く取る**。 LZ の最初の崩れは 4% の局面にしか出なかった。 49 局面では 86% しか捕まえない。 今の関門は 49 / 150 局面 x 20 万ノード + 24 局面 x 200 万ノード、 手・nodes・depth・score・pv の全一致、 先に base 対 base。
9. **関門と別に、 新旧 2 経路を同じ exe で両方計算する検算**を回す (`*_VERIFY`)。 関門は探索の結果、 検算は中間値を見る。
10. **その env スイッチは本当にその exe に在るか**。 本番 exe に存在しない切り替えを渡して「同じ条件どうし」を比べていたことがある。 USI option も範囲外の値は黙って捨てられる。
11. **時間制の実戦の NPS は A/B に使えない**。 同じ exe が run ごとに +69% 揺れた。


## 3. ビルドだけで取れた分

### 3.1 `-march` の 1 行で +10% (07-31)

やねうら王の Makefile の AVX2 ターゲットは `-march=corei7-avx` (Sandy Bridge) です。 この指定で clang は 256 bit の unaligned load / store を 128 bit x 2 に割るコードを出します (Sandy Bridge では速かったため)。 `-march=native -ffp-contract=off` に替えると NPS が約 +10% (504,975 → 中央 約 554k)、 bench のノード数は一致しました。 `-ffp-contract=off` は FMA の自動生成で float の結果が変わらないようにするためです。 本家の HEAD (11-16) にも同じ行が残っているので、 提案の第一候補です (`UPSTREAM_PROPOSALS.md`)。

→ `speedups/S05_compiler_flags.md`

### 3.2 PGO は採取の条件で結果が決まる

clang の instr PGO で +7〜9% (07-14) を得た後、 9 月に「PGO 版のほうが遅い」事件がありました。 原因は**採取のときに存在しない net のパスを渡していた**ことで、 評価関数の熱い経路が profile に入っていませんでした。 実在の net で採り直すと −7.0% → +7.0% に反転しました。 その後も「ホットパスを変えたのに profile を採り直さない」と害が出ます (採り直しだけで +3.08% [+0.65, +5.48] 20 周、 09-30)。 `make clean` が p2nnue のオブジェクトを消し残して、 計装ビルドでも評価の経路が profile に入らなかったこともあります (09-01、 採り直しで +11.0%)。

点検項目: ①採取のログで net が読めたことを確かめる ②採取は配布する net 一式と本番の option で ③熱い経路を変えたら採り直す ④clean が本当に全部消したか確かめる。

→ `speedups/S04_pgo_procedure.md`

## 4. 税の正体を探す — 分岐予測ミス

threat の税 (11-05、 threat を剥いだ net 比で 22.3%) を分解すると、 ほぼ全部が**列挙** (攻め駒を走って対を作る部分) でした。 列挙の関数の中の計算量を減らす試み (表を小さく、 popcount で、 L1 に常駐) はどれも効かず、 「税の 96% は列挙関数の外にある」という不思議な結果も出ました。

決め手は次の測定です。

```
列挙の税、 初めての局面 (cold)            20.4%
列挙の税、 同じ局面を 4 回繰り返す (warm)   14.5%
差 5.9pt は「初回だけ払う」もの
表を L1 に常駐させても +0.96pt、 表を温めておくと −2.3pt (キャッシュでは説明がつかない)
```

同じ局面を繰り返すと消える費用は、 分岐予測器が学習して消える費用です。 列挙は「攻め駒 30 枚 x 利きの方向 x 標的の有無」で trip count が局面ごとに変わるループの集まりで、 ループの出口の予測ミスが税の本体でした。 したがって表を小さくしても走査が変わらない限り取り戻せず、 **走査そのものを減らす** (= 変わった駒の分だけ差分で更新する) しかありません。 これが LZ につながります。

並べ替えで分岐を揃える案 (攻め駒をクラス順に回す、 lossless) も試し、 計測ビルドで +3.16% 出ましたが、 本番相当のビルドでは +0.5pt [−1.5, +2.3] で、 閉じました (2 章の 5)。

→ `speedups/` には仕様を立てていません (分析)。

### 4.1 利きライブラリを外す (11-05)

税を調べる途中で、 本家の長い利きライブラリ (`LONG_EFFECT_LIBRARY`、 do_move ごとに利きを差分で更新する) が threat のために有効になっていたことの費用が大きいと分かりました。 threat の列挙に要る利きは、 magic bitboard で局面から直接出せます。 外すと非 PGO で 108.88% [106.70, 111.18] (6 周)。 ただし 1 手詰めの判定が LE 版と利きなし版で変わり、 探索の木が変わるので、 1 手詰めも利きなし版に固定しました (`P2_MATE1PLY_NOEFFECT`)。 PGO を採り直した後の本番比は、 同時に入れた先読み pf4 と合わせて +3.91% [+2.44, +5.62]、 さらに pf4 の guard のバグ (本番で一度も走っていなかった) の修正を含めて +7.96% でした。

→ `speedups/S01_drop_long_effect.md`

## 5. LZ — threat の多段 lazy 差分更新

### 5.1 2 度の失敗

- 7 月: Stockfish 式に、 do_move のたびに「変わった threat の index の列」を作って StateInfo に持つ形 (dirty threat)。 **−22.7%**。 使われない差分 (評価されない node、 刈られる node) を毎手作るのが費用だった。
- 10 月: 「親の accumulator が valid で、 同じ群のときだけ差分」。 NPS は ±1% で効果 0、 rdtsc で差分 / 全計算 = 0.81〜0.86 と出て「構造的に赤字」として閉じた。 ところが本当の原因は**親が valid な割合が 34.7% しかない**ことで、 差分の機会そのものが少なかった。

### 5.2 考え方

本番の評価の **99.2%** が全計算でした。 一方で 1 手で本当に変わる攻め駒は平均 1.78 枚です。 そこで評価の時点で (do_move ではなく、 使うときだけ):

```
評価する node C
  └ 祖先を最大 DMAX=8 手さかのぼり、 「両視点 valid かつ 同じ群」の祖先 P を探す
     見つからない → 従来の全計算 (full)
  └ 盤を 1 手ずつ巻き戻しながら、 各手の Δ (足す対・引く対) を作る
  └ acc(C) = acc(P) + Σ Δ。 途中の祖先にも acc を書く (物質化)
     → 次の兄弟は d=1 の差分で済む (適用率 43% → 85%)
```

1 手の Δ は、 動いた駒 (A → B) と取られた駒、 そして A・B に利いている駒 (A・B を通る飛び駒のレイが変わる) だけから作れます。 飛び駒のレイが変わったかは「動く前と後の occupancy の共通部分で A か B に届くか」と同値なので、 `between_bb` は要りません。 i16 の wrapping 加算は可換で、 引くのは足すことの厳密な逆元なので、 足し引きの順序に依らず全計算と同じ値になります (bit 一致)。

### 5.3 崩れた例と直し方

最初の実装は 49 局面中 2 局面で探索の nodes が僅かに違いました (+26 / +10)。 原因は、 **物質化が「valid だが群の違う」祖先を上書きしていた**ことです。 さかのぼりは「valid かつ同じ群」で止まるので、 valid だが群が違う node は素通りして途中の列に積まれ、 そこへ今の群の acc を書いてしまう。 その node が root の反復深化や aspiration の再探索で自分の bucket で再評価されると、 別の群の表の acc を使い、 静的評価が変わって木が変わりました。 直し方は 2 つ: (A) valid が立っている node には物質化で一切触らない、 (B) 全計算の経路の valid 判定にも群の一致を要求する。 これで 223 局面 (49 + 150 局面 x 20 万、 24 局面 x 200 万) が全一致しました。

この崩れは、 「key だけ書いて acc を書かない」影の probe では再現しませんでした。 差分経路の検査は書き込みの副作用まで含めないと本番の崩れを映しません。 もう 1 つ、 全計算の経路で新たに bucket を計算すると進行度の float 加算の経路が変わって bit 一致が崩れるので、 bucket は呼び出し元から受け取るだけにしています。

### 5.5 いま残っている「全計算に落ちる」分

LZ の後の threat の費用は評価 1 回あたり平均 2,892 cycle で、 その内訳は d=1 の差分 56%、 全計算に落ちた分 21% です (11-11)。 全計算に落ちる 414,624 回 (5M ノードあたり) のうち 315,320 回は「64 手さかのぼっても同じ群の valid な祖先が無い」もので、 OPN が入ってからは root が序盤 (OPN の帯) の探索で、 root から本体の帯へ移る node が基点を持たないことが主因と分かりました (OPN の帯では本体も threat も計算しないため)。 全計算は自分の node にしか書かないので、 同じ親の次の子もまた全計算になります。 対策が BACKMAT (`-DP2_LZ_BACKMAT`、 全計算した子から親を逆向きの差分で作る) で、 上限は約 +2.2%、 見込み +0.8〜1.6% でしたが、 NPS の A/B では線に届かず採用しませんでした (11-17)。

→ `speedups/S11_threat_lz.md`、 `S12_lz_idxv2.md`、 `S13_lz_rowpf.md`、 `S16_lz_d1fast.md`、 `S25_lz_backmat.md`。

## 6. forward と配置・固定費

- **fc0 の重みが 48 mod 64 に落ちていた** (09-29)。 `std::vector` で確保した重みが 64 B 境界に乗っておらず、 評価のたびに 256 本の split load (キャッシュラインをまたぐ load) を出していました。 64 B 整列の allocator に替えて +1.93% [+0.32, +3.76]。 本家の NNUE はもともと `alignas(64)` なので本家には関係ありません。 → `speedups/S07_fc0_alignment.md`
- **`__chkstk` の除去**: 多段の差分更新の作業配列 300 → 128 で関数のフレームを 4.7 KB → 3.3 KB にし、 Win64 で毎評価 2 回呼ばれていた `__chkstk` を消した。 threat の差分が無効な net で priming の threat を作らない、 bucket の再利用と合わせて +4.81% (壁時計、 8 round)。 → `speedups/S08_fixed_cost_cleanup.md`
- **fc0 は AVX2 では疎より密**: Stockfish 式の疎な fc0 (非零の 4 byte chunk だけ積和) を 3 回試し、 3 回とも負け (最後は 64 周で 98.84% [98.24, 99.48])。 非零 chunk の率が約 70% と高く、 fc0 は port 0/1 の積和の throughput で律速しているためです。 🚨VNNI のある CPU では結論が変わりえます。
- **先読みはほぼ全滅**: FT 行を do_move で 16 line / 全部、 correction history、 MovePicker、 Finny 表、 OPN の差分行を do_move で… どれも区間が 0 をまたぐか負。 通ったのは「行の index が決まった瞬間に出す」もの (ROWPF、 OPN の F2) だけで、 先読みはリード時間が取れる位置で出さないと効きません。 11-06 に採用した pf4 (do_move で FT 行の先頭 4 line) は、 LZ の後では有害 (98.77% [98.33, 99.23] 128 周) になって外しました。 採用した結論が後で覆った例です。
- **final2 (採用)**: 本家のやねうら王を読んで見つけた 2 つの形と、 OPN で効いた 1 つを本体に当てたもの。 3 本を一緒に入れた exe で、 検算 (新旧の経路の照合) は不一致 0、 関門 3 本 x INFREP off/on は完全一致、 NPS は 28 周で打ち切って 101.74% (区間なし、 3 本の合計) でした。
  - F01 `P2_TR_STORE32`: transform の出力を 16 列ごと 8 byte x 2 回の store から、 32 列ごと 32 byte 1 回の store に。 片側の `max(0)` を省く (負 x 正は mulhi の後で負になり packus が 0 にする)。
  - F02 `P2_ACC_PIECEWISE`: 多段の追いつきで、 駒番号ごとに「祖先での位置」と「今の位置」だけを残す (途中で 2 回動いた駒も 1 対で済む)。 本家の `update_from_computed_ancestor` と同じ考え方。 検算では 2 手以上の追いつき 35,720 回で行の本数が 354,714 → 282,774 に減った。
  - F03 `P2_FC0_PF`: 本体の fc0 の重みを 2 KB 先まで先読み (OPN の F2-1 と同じ核)。

  → `speedups/F01_tr_store32.md`、 `F02_acc_piecewise.md`、 `F03_fc0_pf.md`

## 8. 2 本目の net を遅くしない

## 9. Lazy SMP の診断と独自の機構

配布の既定は Threads 4 です。 確認対局は Threads 1 なので、 ここは対局の結果には効いていません。

### 9.1 診断: thread を増やしても速くならない

```
time-to-depth (3 thread / 1 thread) = 0.98 倍 [0.91, 1.05] (depth 15、 120 局面 x 2)
                                     0.97 倍 [0.92, 1.03] (depth 18、 200 局面)
1 thread あたりの木 = 1 thread の木の 0.93〜0.95 倍 = 92〜95% が重複
```

Lazy SMP の thread 間の違いは aspiration の初期窓のずらし (`base + threadIdx % 8`) の 1 か所だけで、 各 thread がほぼ同じ木を時間差で読んでいました。 置換表の共有で節約できるのは 5〜8% です。 🚨 ただし 11-22 に局面のキーで数え直すと、 thread 間で重なる局面は 21〜25% でした。 「92〜95% が重複」は 1 本あたりのノード比から出した見立てで、 そのまま「同じ木を何度も読む」とは言えません。 SMP の機構を選ぶ前に、 この前提を測り直す必要があります。 NAGISA v4 もやねうら王の Lazy SMP なので、 この性質は我々に固有ではありません。

### 9.2 試した機構

| 機構 | 中身 | 結果 |
|---|---|---|
| aspiration のずらしを強める | `delta += STEP * (threadIdx % 8)` | 採用に至らず |
| continuation history の共有 | per-thread 53.7 MB を共有 (Stockfish が 2026-06 に共有へ戻した変更と同種)。 構築時に確保 (遅延確保は data race) | 採用に至らず。 メモリは 161 → 54 MB |
| ABDADA 風の後回し | 他 thread が展開中の子を末尾へ | 発火率 0.025%/thread。 我々の重複は「読み終えた節の時間差の重複」で ABDADA の的と違う |
| 根の YBWC | 根の 2 手目以降を helper に配る | 根では 1 手目が木の大半を使うので配る仕事が少ない |
| null move の thread 別ずらし | R を thread の偶奇でずらす | 効果なし (摂動では時間差の重複は減らない) |
| **M4: 置換表を介した仕事の委譲** | 内部節で 2 手目以降を helper に提示し、 helper は読んだ結果を置換表に書くだけ。 master は全手を自分で読むので、 helper が遅れても落ちても結果は helper 不在と同じ | 動作確認 (n=8、 depth 16) で time 0.975 倍 → md8 で **0.710 倍**。 Threads 4 の正式判定はしていない。 11-21 に時間切れ停止時の不具合が見つかり、 直した版でも対局で改善が見えなかったので既定 off のまま |

→ `speedups/P06_m4_tt_delegation.md`

### 10.2 教訓

1. **測り方の分解能を先に計算する**。 狙う効果量が今の周回数で見えるかを、 測る前に確かめる。
2. **計測ビルドの得は本番ビルドに移らない**ことがある。 採否は本番相当のビルドで。
3. **PGO は非 PGO の得の半分前後を既にやっている**。 非 PGO の数字で期待しすぎない。
4. **先読みはリード時間がある場所で出す**。 「早く出す」ではなく「index が決まった瞬間に出す」。
5. **閉じた結論も採用した結論も、 条件が変われば覆る**。 10 月の差分は LZ で覆り、 pf4 は LZ の後で有害になった。 閉じるときは条件を書いておく。
6. **関門は不具合を捕まえる広さで**。 4% の局面にしか出ない崩れがあった。 差分経路の検査は書き込みの副作用まで含める。
7. **原因の機構を測ってから対策を選ぶ**。 threat の税をキャッシュだと思っていた間は、 何を足しても効かなかった。
