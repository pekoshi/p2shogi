# 今後の課題 (引き継ぎ)

p2shogi v9 の公開 (2026-11) で開発はいったん終了します。 ここには、 続きをやる人 (未来の我々を含む) のために、 分かっていることと、 次に試す価値があると考えたことを書きます。 優先度は我々の見立てで、 根拠の強さを「実測」「推測」で分けました。

## 0. 現在地の要約

- 同じ時間で相手 (NAGISA v4) より多く読めている (時間制 1 手 1 秒で 1.12 倍のノード、 +1.0 ply。 11-06)。 それでも対 v4 は 40% 前後です (11-10 の版で 40.0% [36.8, 43.1]。 v9 は同ノード 30 万で 38.0% / 200 局、 1 手 1 秒 Threads 1 で約 39.5% / 100 局)。 **残る差は評価の質**と読んでいます。
- floodgate では v9 (Core i7-7700 の 4 スレッド、 定跡なし) がレート 4248 (11-23、 28 局)。 レート 4300 以上の相手には 1 勝 10 敗 3 分で、 実力は 4250 前後と見ています。
- 静的評価の質 (篩) の差は**序盤 (bucket 0〜2) に集中**し、 bucket 3〜7 は並んでいます (順位相関 我々 0.283 / v3.1 0.311 / v4 0.341、 11-12)。 序盤は OPN で 0.2555 → 0.3016 まで上げましたが、 v4 (0.3127) には届いていません。
- 評価関数の FT は、 手持ちのどのデータでも「学習」せず「拡散」するだけでした (5 章)。 我々の資源 (GPU 4 GB) では、 FT を一から作り直す道も実験で否定されています。

## 1. bucket 2 の評価の弱さ

| net | bucket 2 の篩 |
|---|---:|
| 我々の本体 (L1) | 0.3937 |
| NAGISA v4 (threat なし、 幅 2304、 OPN と同じ型) | 0.4125 |

- 分かっていること (実測): OPN を bucket 2 へ延長すると 0.369 で頭打ち。 OPN に bucket 2 だけ追加学習すると bucket 0 を −0.030 壊す。 本体の bucket 2 の head だけを作り直す案、 bucket 2 専用の本体、 FT を `--loss-scale 300` で動かす案はすべて閉じました。 v9 の後には OPN を bucket 0〜1 に広げる設定と、 OPN を FT も動かして学習し直す案も試しましたが、 どちらも対局で勝てませんでした。
- v4 は threat なしでも bucket 2 で我々を上回る。 → 差の本命は threat ではなく **FT の質 (学習器・データの使い方)** と読んでいる (推測)。 v4 と我々は学習データの出所が同じ (v4 の作者が公開している ponkotsu 系) ので、 データそのものより学習器・構造の差を疑う。
- 次の一手の候補: (a) 幅 2304 の threat なし FT を bucket 2〜3 用に持つ「2 本目の OPN」(序盤用 OPN の作り方を中盤の入口に) (b) BulletOu / tatara の学習設定 (WRM・|score| の除外・dual-label など、 本家にあり我々に無いもの) で FT を作る。 どちらも GPU 数日〜数週。

## 2. 地平線問題と評価の楽観 (探索で補う)

### 2.1 実例

| 局 | 局面 | 何が起きたか |

- 悪手の分析 (実測): v4 の評価が 150cp 以上落ちた手のうち、 深読みで悪手と確定したのは 4 割。 確定した悪手は「際どい局面の出目」で、 同じ局面を白紙から読み直すと 21 手中 13 手で正解を選ぶ。

- 評価の楽観 (実測): 負けた局で我々の静的評価が v4 より +68cp 甘く見えるのは、 大部分が**選択の偏り** (負ける側は自分の net に好かれる局面へ歩く。 鏡像で v4 にも同じ大きさで出る)。 鏡像で対照を取っても残る非対称は 1 秒探索の値で 23〜41cp。

## 3. threat の全幅化

我々は threat の出力を 64 列に絞りました (速さのため)。 threat を FT の全幅 1024 列に入れれば篩は上がると見込んでいますが、 accumulator の費用が 16 倍になります。 **全幅の threat を、 我々の LZ 並みの速さで回せるか**が最も大きな未踏の問いです。

### 3.1 構造の比較 (各配布物の説明とソースから)

| 項目 | p2shogi (v9) | NAGISA v4 |
|---|---|---|
| 駒の特徴 | HalfKA_hm (鏡像 45 区分、 73,305) | HalfKA_hm2 |
| FT の幅 | 1024 | 2304 |
| threat | 216,720 → **64 列** (群化 4 群) | なし |
| threat の更新 | LZ (評価時に最大 8 手の多段差分 + 物質化) | — |
| PSQT | あり | なし |
| KH (浮き駒) | あり (78 → 64) | なし |
| LayerStack | 進行度 8 (NAGISA v3.1 の progress.bin) | 9 (玉 3x3) |
| FT 後段 | 1024 → 16 (15 + skip) → 30 → 64 → 1 | 同系 |
| FT の型 | i16 (刻み 254 x 8) | i16 |
| L1 の刻み | 1/128 (L1Q128)、 fc1 も 1/128 (FC1PREC) | (未確認) |
| 序盤専用 net | OPN (幅 2048、 K16、 v9 では bucket 0 だけ) | なし |
| Finny | あり | あり |
| 差分の連鎖を保つ工夫 | 多段の追いつき (最大 128 手、 駒単位に畳む) | — |
| FV_SCALE | bucket ごと 26〜28 | 28 (対局で渡した値) |

### 3.2 次の一手

- **K probe**: 今の net の threat の表を K 列にゼロ詰めで広げた net (評価値は K=64 と同じ) で、 列を増やしたときの NPS の費用だけを測る。 これで「全幅にすると何 % 遅くなるか」が学習なしで分かる。 公開前に回す予定でしたが、 優先度を下げて回していません。
- 全幅の threat の net を学習する (表は i8 で 216,720 x 1024 x 4 群 ≈ 890 MB、 学習時は f32 と optimizer の状態でその数倍。 4 GB の GPU では群を減らすか群なしにする必要がある。 推測)。
- 全幅では accumulator の加減算が 16 倍になるので、 LZ の d=1 の apply (今 569 cycle) が支配的になる。 FT を i8 にする工夫は、 我々の AVX2 では負けた (96.06%) が、 列が 16 倍なら条件が違う。
- threat 入力の倍率 (k = 0.90 / 1.05 / 1.10 を掛ける) は v9 の後に試し、 どれも対局で負けました。 64 列の中身を変えずに効き方だけを変える調整は、 余地が小さいと見ています。

## 4. threat の差分更新の続き

- BACKMAT (全計算に落ちたら親へ逆向きに物質化) は 11-17 に実装して試し、 probe では移り目の局面で threat の cycle −16.4% でしたが、 NPS の A/B では線 (+1.0%) に届かず不採用にしました (`speedups/S25_lz_backmat.md`)。 中盤の局面では「群をまたぐ」全計算が残っています。
- 群をまたぐ兄弟の救済 (天井 +1.5%、 現実 +0.7%、 推測)。
- do_move の直前の手から駒レベルの差分を作り、 王手の局面でも評価して連鎖を保つ方式と、 LZ (評価時の多段差分 + 物質化) の比較は未実施。 全幅にするなら両方を測る価値がある。

## 5. FT の学習の知見 (失敗の記録)

- **FT は手持ちのどのデータでも学習しない**。 移動量は lr に比例、 step の平方根に比例 (= 向きの揃わない拡散)。 5 データの指数 α ≈ 0.5 (方向のある学習なら 1.0)。 現職自身のデータと未見を狙ったデータが区別できなかった。 新しいデータは、 まず 15 分の probe (500〜2000 batch の 4 点で α) にかけ、 α が 0.7 を超えたときだけ本学習に賭ける。
- **FT を `--loss-scale 300` で動かしても、 データの系統で壊れる** (11-16): ponkotsu 系 (lr 1.2e-5、 bucket 2-7) で bucket 3-7 を −0.0141 ±0.0019 壊し、 bucket 2 は +0.0033 ±0.0076 で伸びず。 dlsuisho 系だけにすると壊し方は 1/10 (−0.0015 ±0.0013) だが bucket 2 は伸びない (−0.0037 ±0.0046)。
- **FT を大きく動かすと弱くなり、 一から学習しても追いつけない** (実験済み)。 だから OPN は本体の FT を写して出発し、 本体は FT を凍結して fc0 と KH だけを学習した。 v9 の後に OPN を FT も動かして学習し直した版も、 対局で勝てなかった。
- 容量 (幅 1536 など) とデータ軸 (9 本) は閉じた: FT が学習しないので新しいユニットは乱数のまま。
- **量子化の誤差は「直せば強くなる」とは限らない** (v9): FT と後段の刻みを細かくして整数推論の誤差を減らした net は、 そのままでは対局で弱くなった。 古い量子化にあった「手番側を悲観的に見る片寄り」が楽観のブレーキになっていたと読み、 bucket 補正で片寄りを足し戻している (`TECHNICAL_NOTES.md` 2.7)。 片寄りの量と勝率の関係は 40 局ずつの対局しかなく、 確かめ切れていない。

## 6. 大きな環境なら、 どこから手を付けるか

我々の制約は GPU 4 GB 1 枚・CPU 4C/8T でした (`OVERVIEW.md` 5 章)。 資源があるなら、 我々なら次の順で手を付けます (推測)。

1. **FT を作り直す**: 大きな GPU で、 本家側の学習器 (BulletOu / tatara) の設定を使い、 HalfKA_hm2 系の FT を一から学習する (我々の資源では 1 回 数週間で、 しかも負けた)。 bucket 0〜2 の篩が v4 を超えるかを最初の関門に。
2. **threat を全幅に**: 3 章の K probe を回し、 全幅の net を学習し、 LZ で回す。 FT の i8 化も試す。
3. **評価の改善を対局で確かめる枠を広げる**: 我々は対局を同時 2 本までしか回せず、 1,200 局で 2SE ±3pt が限界だった。 +2pt の改善を測るには数千局が要る。 局面集の前半と後半で 20pt 違うこともあったので、 局面集も複数で。
4. **多 thread の探索**: M4 と continuation history の共有を、 8〜32 thread で測る。 我々の機械では Threads 4 が上限。
5. **VNNI / AVX-512 の CPU で fc0 を測り直す**: 疎な fc0 (我々は AVX2 で負け) と i8 FT の結論は CPU で変わりうる。
