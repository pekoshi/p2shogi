# p2shogi 技術解説

p2shogi v9 がどう動いているか、 なぜそう作ったかを、 通して読める形でまとめました。 実装の場所と切り替え方は `MECHANISMS_GUIDE.md`、 改造点の一覧は `CHANGES_FROM_UPSTREAM_engine.md`、 速さの話は `SPEEDUPS_STORY.md` にあります。 数字は特記がなければ我々の機械 (Core i7-7700、 AVX2) での実測です。

## 1. 全体像

p2shogi は、 やねうら王 (V9.40、 `717da87`) の探索に、 独自の評価関数 P2NNUE を載せたエンジンです。

- **探索**はやねうら王 (Stockfish 系) のコードをほぼそのまま使い、 定数を USI option に出して SPSA で合わせました。 独自の変更は少数です (3 章)。
- **評価関数**が開発の中心です。 NNUE の標準形 (HalfKA_hm + LayerStack) の上に、 駒の当たりを直接見る **threat 入力**、 浮き駒を見る **KH**、 序盤専用の別の net **OPN** を載せています (2 章)。
- 開発の制約は機械でした (GPU 4 GB 1 枚、 CPU 4C/8T)。 net の幅・データ量・試行回数、 そして測定の分解能が、 ここで決まりました (4 章)。

評価 1 回の流れ:

```
局面 ─┬─ 進行度 (progress.bin の係数で計算) ─> bucket 0〜7 を選ぶ
      │
      ├─ 序盤 (OPN_ProgHi より前、 v9 では bucket 0) ─> OPN (幅 2048) だけで評価
      │
      └─ それ以外 ─> 本体:
           HalfKA_hm の FT (1024 x 2 視点、 差分更新)
           + threat acc (64 列、 評価のときに多段の差分で作る = LZ)
           + KH (浮き駒 64 列、 評価のときに一時 buffer で)
           → transform (対の積) → fc0 → fc1 → fc2 (bucket ごとの重み) + PSQT
           + bucket 補正 (先手番 / 後手番の探索で別の表)
           → FV_SCALE (bucket ごと) で目盛りを合わせて評価値
```

## 2. 評価関数 P2NNUE

### 2.1 主入力と FT (HalfKA_hm、 幅 1024)

主入力は NNUE の標準形の HalfKA_hm です。 自玉の位置 (左右の鏡像で 45 区分) と、 全駒の位置・持駒の組 73,305 次元を、 FT で 1024 列 x 2 視点 (手番側と相手側) の累積器にします。 駒が動いたら変わった行だけを足し引きし (差分更新)、 玉が動いたら Finny 表 (玉の区分ごとに最後に作った累積器を覚えておく表) から作り直します。 何手も評価していない node では、 計算済みの祖先まで最大 128 手さかのぼって、 途中の手をまとめて足し引きします。

transform は `clamp(0..254)` した前半 512 列と後半 512 列の対の積で、 fc0 の入力 1024 本を作ります。 形は本家の SFNN (`SFNN_halfkahm2_1024_15_64_*`) とほぼ同じで、 違いは上に載せた threat・KH・OPN と LayerStack の選び方です。 P2NNUE は本家の `eval/nnue/` を使わない独立の実装で、 当初ラム将棋の fork (Rust) で書いたものを C++ に移しました。

### 2.2 threat 入力と LZ

**threat** は「どの駒がどの駒に利いているか」の対 (攻め駒・標的・相対位置。 玉は攻め駒にも標的にも入れない) を 216,720 次元の疎な入力にしたものです。 駒の当たり・ひも・浮き駒を、 評価関数が数手読まずに直接見られるようにするのが狙いです。 7 月に入れ、 「full threat 搭載」として公表しました。

threat の出力は FT の全幅 (1024 列) ではなく **64 列**に絞り、 前半 32 列を FT の [0,32)、 後半 32 列を [512,544) に足しています (対の積の両側に対称に入れるため)。 9 月に出力幅 K を掃引し、 税 (NPS の低下) が K=1024 で −37.5%、 K=64 で −17% だったので 64 にしました。 64 列なら 1 行が i8 で 64 B = 1 キャッシュラインに収まります。 学習時は bucket を 4 群 (0 / 1-2 / 3-4 / 5-7) に分け、 群ごとに別の表を持ちます。

それでも税は threat を剥いだ net 比で 22〜30% 残りました。 11-05 に分解して、 その本体が**分岐予測ミス**だと分かりました。 同じ局面を 4 回繰り返すと列挙の税が 20.4% → 14.5% に下がり、 表を L1 に常駐させても +0.96pt しか戻らなかったからです。 列挙は「攻め駒 30 枚 x 利きの方向 x 標的の有無」で回数が局面ごとに変わるループの集まりで、 ループの出口の予測を外すのが費用でした。 表を小さくしても走査が同じなら取り戻せず、 **走査そのものを減らす**しかありません。

そこで作ったのが **LZ (多段 lazy 差分)** です。

- do_move では何もしない (評価されない node の差分を作らない。 do_move で毎手差分を作る Stockfish 式は −22.7% だった)。
- 評価のとき、 threat acc が計算済みの祖先まで最大 8 手さかのぼり、 途中の手で変わった対だけを足し引きする。
- さかのぼれないときは全計算し、 その結果を途中の node にも書いておく (物質化) ので、 兄弟の node が使える。
- 群が違う祖先は使わない。 物質化で valid な祖先を別の群の値で上書きして崩れた例があった。

LZ は PGO 同士 128 周で +2.25% [+1.69, +2.87]、 その後の仕上げ (index 計算の hoist、 行の先読み、 1 手ぶんの専用路) と合わせて数 % を取り戻しました。 全計算した子から親を逆向きに作る BACKMAT は、 probe では移り目の局面で threat の費用 −16.4% でしたが、 NPS では線に届かず採用しませんでした。

### 2.3 KH (浮き駒)

**KH** は、 どの駒にも守られていない駒 (浮き駒) を 78 次元の入力にし、 64 列にして threat と同じ FT の位置に足すものです。 評価のときに threat acc + KH 行を一時 buffer で作るので、 StateInfo の累積器を書かず、 LZ と独立です。 学習では本体の FT・threat・fc1・fc2・PSQT を凍結し、 KH と fc0 だけを 4 SB 学習しました。 FT を動かすと弱くなる (2.9) ので、 「FT を凍結して新しい入力 + fc0 だけを学習する」形にしています。

篩 (4.1) の KH on − off は bucket 0〜2 で +0.0055 ±0.0022、 3〜7 で +0.0048 ±0.0009、 NPS の税は −0.34% [−0.93, +0.26] で、 見積もり (−4〜−9%) より大幅に小さく済みました。 配布の `kh.bin` は学習した重みを 1.25 倍したものです。

### 2.4 LayerStack と進行度

fc0 以降は LayerStack で、 進行度で選んだ 8 個の bucket ごとに別の重みを持ちます。 進行度は「玉と駒の絶対位置 (KP-Absolute) の重みの和」で、 その係数は NAGISA v3.1 の `progress.bin` (GPLv3) を使い、 bucket の閾値も NAGISA と同じです。 層は fc0 1024 → 16 (15 本 + skip 1)、 sqr_crelu と crelu の連結 30 → fc1 64 → fc2 1 です。

試して採らなかったもの: 進行度 x 持駒の 16 bucket、 4 層目、 幅 1536、 narrow 1024-8-64 など。 FT が学習しない (2.9) ので、 容量を足しても新しいユニットが乱数のまま残りました。

### 2.5 OPN (序盤専用 net) と継ぎ目

序盤の静的評価は本体が最も弱い帯で (篩 bucket 0-1 で本体 0.2555 対 NAGISA v4 0.3127)、 そこを別の net で受け持つのが **OPN** です。

- 幅 2048、 入力は HalfKA_hm K16 (玉区分 16 = 自玉 7〜9 段 x 5 筋 + その他) + factoriser。 threat も PSQT も無い。
- 本体の FT を、 幅 2048 の半分の列に写して出発する。 一から学習した幅 2048 は同じ 2 SB で篩 0.2050、 写しから始めると 0.2756 だった。
- 教師は DL 水匠のラベルを付けた公開データ (dlsuisho-ponkotsu-distilled) から、 進行度 bucket 0〜2 の局面だけを抜いたもの (約 17 億局面)。 `--loss-scale 300` で教師の勝率変換の目盛りを変え、 互角付近に勾配を配った。 最後の 3 SB は QAT。
- 篩 bucket 0-1 は 0.3016〜0.3019 (本体 0.2555 から +0.046)。

切り替え (継ぎ目) は進行度から重み λ (0〜256) を作って OPN と本体を混ぜる仕組みですが、 公開版は混ぜる幅を 0 にしています。 λ が 256 か 0 だけになり、 OPN の局面では本体も threat も計算しないので速いからです (幅 2048 の素の実装は本体の約 80% の NPS で、 高速化 2 段と幅 0 で 1 手 1 秒の到達ノードを対 v4 110% まで戻しました)。 v9 の継ぎ目は `OPN_ProgHi=-1946` で、 OPN が受け持つのは進行度 bucket 0 だけです。 bucket 0〜1 を受け持たせる設定は対局で負けました。

### 2.6 量子化の精度 (L1Q128・FTI32 系・FC1PREC)

学習器は f32 で学習し、 エンジンは整数で推論します。 学習器の量子化は FT が 254 刻み (QA=127 の対の積)、 層の重みが 1/64 刻み (QB=64) です。 この丸めが、 際どい局面で手の順位を入れ替えていました。 python で f32 と整数推論を比べると、 同じ親の子どうしで評価の差が 10〜30cp の帯の 20.5% で、 最善手が入れ替わっていました。

v9 では、 学習し直さずに f32 の重みから 3 段で書き直しています。

| 段 | 中身 | 入れ替わり率 (10〜30cp 帯、 python) | NPS |
|---|---|---|---|
| 従来 | FT 254 刻み、 fc0 1/64 | 0.205 | — |
| L1Q128 | fc0 の本体 15 行を 1/128 刻み (i8、 飽和させる) | (篩 bucket 2-7 で +0.0027 ±0.0009) | 99.75% (非劣化) |
| FTI32 系 | FT の重み・bias を 254 x 8 刻みの i16 で持ち、 transform の出力を i16 (0..126x32) にして fc0 を i16 入力の積和に。 その fc0 を非零の 2 列単位で回す疎な版にする | 0.057 | −6.53% [−7.21, −5.90] |
| FC1PREC | fc0・fc1 の活性を 2 ビット細かく (0..508)、 fc1 の重みを 1/128 刻み | 0.019 (f32 の後段の天井とほぼ同じ) | 影響なし |

設計で効いた判断:

- **累積器は i16 のまま**にした。 FT の刻みを 8 倍にすると和が i16 に入るかが問題になるが、 探索中 3,226 万回の transform で和の範囲を実測すると [−9,057, 12,019] で、 i16 に 2.7 倍の余裕があった。 i32 にする版 (`-DP2_FT_I32`) も作ったが、 結果が同じなので使っていない。
- **threat と KH は従来の目盛りの別の累積器**のまま持ち、 transform で 8 倍して足す。 threat 表の値は 1 bit も変わらない。
- transform の命令数を変えないように、 shift の組を `mulhi(lo << a, hi << b)` に収めた。 fc0 は i16 入力で計算が約 2 倍になるので、 非零の組だけを回す疎な版で取り戻した。
- 形式を変えるたびに arch の token と版番号を変え、 古い exe が新しい net を黙って読まないようにした。

### 2.7 bucket 補正と先後別の表

精度を上げた net は、 **そのままでは対局で弱くなりました** (同ノード 20 局で 27.5%、 「壊れていない」の線 40% に届かず)。 誤差を調べると、 古い量子化には「手番側を悲観的に見る」片寄りが bucket ごとにあり (例: bucket 2 で −30cp 前後)、 精度版ではそれが小さくなっていました。 我々は、 この片寄りが読み筋への楽観のブレーキになっていたと読みました (仮説。 40 局ずつの対局しかなく、 確かめ切れてはいません)。

そこで、 本体の評価に bucket ごとの定数を足す **bucket 補正**を入れました。 片寄りを打ち消す向きに足すと崩れ (0 勝 5 敗で中止)、 古い片寄りをそのまま足し戻した腕が最良でした (40 局で 40.0%。 他の腕との差は 2SE の内)。 その後、 自己対局の SPSA で表を調整し、 さらに先手番と後手番の探索で別の表を持つようにしました。

- 後手番の探索の表 = SPSA24 の 29 周目の値、 先手番の探索の表 = 古い片寄りを足し戻した値。
- `P2_SENTE_TABLE_SWITCH_CP=500`: 同じ対局の直前の手の root の評価値が +500 以上なら、 後手番でも先手の表を使う (優勢になったら先手の表の性格で押し切る)。
- 表は探索の開始時に 1 回だけ選ぶ。 評価の熱い経路には分岐を足さない。

注意点が 2 つあります。 評価が「局面と root の手番」の関数になるので、 局の境目で `isready` を送らない使い方では、 別の手番で作った評価が置換表から再利用されえます。 また bucket 0 は OPN が先に値を返すので、 bucket 0 の補正は効きません。 その効かない鍵が SPSA で約 20cp 動いたことは、 SPSA の値の 20cp 程度の動きは雑音でも出る、 という物差しになりました。

### 2.8 FV_SCALE

評価値の目盛り FV_SCALE は bucket ごとに持ちます (v9: 26 / 26 / 27 / 28 / 28 / 28 / 28 / 28)。 精度版にしたときに bucket ごとの評価値の SD を測り直しましたが、 変化は ±3% の内で値は変えていません。 🚨 FV_SCALE だけを変えても序盤の局面では別の鍵 (序盤用) が効いて no-op になることがあり、 一度これで「完全一致」の誤った結論を出しました。

### 2.9 学習について分かったこと

- **FT は手持ちのどのデータでも「学習」せず「拡散」するだけ**でした。 FT の移動量が lr に比例し step の平方根に比例する (向きの揃わないランダムウォークの形) こと、 符号を反転したデータ (陽性対照) と比べて 0.2〜0.4 倍しか動かないことから判断しました。 本体は FT を凍結し、 OPN は FT を写して出発したのはこのためです。
- **FT を大きく動かすと弱くなり、 一から学習しても追いつけない** (実験済み)。 4 GB の GPU での結論です。
- データの軸 (注入率・中盤の分布・教師の平均・配合など 9 本) は全部外れました。

## 3. 探索

### 3.1 やねうら王からの違いと理由

探索はやねうら王のコードのままで、 違いは次の通りです。

| 違い | 理由 |
|---|---|
| 定数を `SPSA_*` option に出し、 SPSA で合わせた | 我々の評価関数は目盛りと速さが本家の想定と違う。 RFP・razoring・qsearch の margin は 9 月に 2 倍、 NMP の margin は半分 (対局での調整)。 遅い静かな手を本家より強く縮める (LMR の手数の項 13 対 本家 65) |
| INFREP: 優等・劣等局面の判定を対局の履歴まで広げる | root より前の局面との持駒の優劣も見る。 千日手は従来どおり root 以降だけ。 劣等は ply >= 2 のときだけ (root の子で返すと root がその手を無条件に選ぶため) |
| `HIST_CONFIDENCE_SCALE` | history の 3 成分が同じ向きのとき LMR を強める |
| `BookExitTimeFix` | 定跡を抜けた最初の手で時間が約 4 割減る本家の挙動を直す (前回評価なし = VALUE_INFINITE) |
| 時間管理の係数を option に | 長手数で先手が時間切れになる床の問題があった |
| SRCH_BUNDLE_A | 結果を変えない高速化 (idiv の定数化など)。 +1.53% |
| 利きライブラリを外す | threat のために有効にしていたが、 外したほうが速い (非 PGO +8.88%、 PGO 後 +3.91%) |

試して効かなかった探索の改造は多くあります。 王手延長、 qsearch の静かな王手、 打つ手専用の contHist、 打つ手の刈り免除、 地平線問題を補う腕 (root の fail-low で窓を広げる、 係数を本家寄りに)、 v9 の後の LMR の係数 2490 (浅く広く読む) など。 我々の実測では、 「探索で評価の弱さを補う」方向は採用まで届きませんでした。

### 3.2 SPSA と既定値の焼き込み

v9 の探索係数は自己対局の SPSA (SPSA24) の 29 周目の値です。 調整した 47 個の option と `SPSA_LMR_TABLE_COEFF_OPENING=2763` を、 `OptionsMap::set_release_default` で USI の既定値と現在値の両方に書き込みます。 以前は 206 個の option を設定ファイルで渡していましたが、 ファイルのパスの option だけで起動した探索が以前の設定と 40 局面 x 100 万ノードで同一であることを確かめて、 置き換えました。

SPSA で学んだこと:

- 道具に θ+ / θ− を二重に入れ替える不具合があり (11-19 に修正)、 それ以前の SPSA の結果は見直しが要った。 器そのものを疑う。
- 効かない鍵 (2.7 の bucket 0 の補正) も約 20cp 動く。 個々の値の動きを「方向が出た」と読まない。
- 表示の既定値と実際の値が 1 違う鍵があった (`SPSA_LMR_TABLE_COEFF_OPENING` 2762 / 2763)。 焼き込みの後は「option なしで同じ探索になるか」を関門にする。

### 3.3 千日手の評価値

`DrawValueBlack` / `DrawValueWhite` の既定は -2 / -2 です。 以前の -53 / +41 は電竜戦の規定 (引き分けを先手 0.4 / 後手 0.6 と数える) に合わせた値で、 floodgate (引き分けは 0.5) では後手が千日手を受け入れやすすぎました。 大会の規定ごとに値を変えてください。

### 3.4 並列

配布の既定は Threads 4 で、 やねうら王の Lazy SMP のままです。 thread を増やしても同じ深さに届く時間がほとんど縮まない (3 thread で 0.98 倍) ことを診断し、 aspiration のずらし、 continuation history の共有、 ABDADA 風の後回し、 根の YBWC、 置換表を介した仕事の委譲 (M4) などを試しましたが、 採用したものはありません。 M4 は時間切れで止めたときに helper の枠を返さない不具合があり、 直した版でも対局で改善が見えませんでした。 「木の 92〜95% を重複して読む」という見立ても、 局面のキーで数え直すと重なりは 21〜25% で、 前提から見直しが要ります。

## 4. 測り方

この開発で最も時間を失ったのは、 速くする工夫や評価の改良ではなく**測り方の誤り**でした。 以下は、 誤りを踏んだ後に固めた形です。

### 4.1 篩 (静的評価の質の物差し)

対局は 1 本の評価に数百〜数千局かかるので、 net の良し悪しをまず**篩**で見ます。

- 局面集: 対 NAGISA v4 の対局から取った 130,965 局面。
- 正解: 10 手先の局面を両エンジンが 1 秒ずつ探索した値の平均。
- 物差し: 静的評価と正解の**順位相関** (Spearman) を手番ごとに計算して平均。 bucket の帯ごと (0-1 / 2 / 3-7 など) に出す。
- 2 本の net の比較は、 同じ局面での差を局単位の bootstrap (400 回) で 2SD を付けて見る (`pair_screen.py`)。

篩で分かったことと注意:

- **SB ごとの揺れが大きい**。 学習の 1 SB ごとの篩の揺れは sd 0.0055 (2σ 0.011) で、 同じ net を局面の半分ずつで測った揺れ (split-half) の 11 倍。 3〜4 SB 続けて動いても傾きとは言えない。
- **帯をまたいで相関を比べない**。 互角帯のように真値の幅が狭い層ほど順位相関は機械的に低く出る。
- **篩と対局は一致しないことがある**。 bucket 補正のような定数の足し算は篩をほとんど動かさないのに、 対局は大きく動いた。 逆に篩の小さな改善 (+0.003) は数百局の対局では見えない。 篩は参考程度に使い、 篩の差で勝敗を予想しない。
- 公開版の篩の正解値は相手エンジンの探索値を含むので同梱していません。 自分で作り直すときは、 局面と正解を自分の対局・自分の探索で作ります。

### 4.2 対局による比較

- **対応ペア**: 同じ開始局面を先後入れ替えて 2 局指し、 局面ごとの得点の差で比べる。 局面の難しさの揺れが消えるので、 同じ局数でも 2SE が小さくなる。
- **局面集を先頭から順に、 全部使う** (`tournament --startpos-sequential`)。 既定の動作は run ごとに局面を抜き直すため、 被覆が 60〜68% で腕どうしの局面が揃わず、 基準の腕を 29.0% と誤って測った (全局面を 1 回ずつ指し直すと 35.0%)。
- **固定ノードと Threads 1** で探索量を揃える。 時間制は NPS と時間管理も含めた最終確認に使う。
- 分解能: 2SE は 135.8/√n pt 前後。 600 局で約 5.5pt、 1,200 局で約 3pt。 +2pt の改善は手持ちの局面数では原理的に測れなかった。

### 4.3 固定ノードの決定性

`go nodes N` は Threads 1 でも、 前の局面の置換表や history が残っていると結果が揺れます (同じ局面 8 回で depth 15〜17)。 局面ごとに `isready` を送ると、 固定ノード Threads 1 の再対局は 80 局すべて同じ結果・同じ手数になりました。 したがって基準の腕は再対局せず、 新しい局面だけを足せば済みます。 🚨 `usinewgame` はこのエンジンでは何もしないので、 置換表を消すには `isready` が要ります。

### 4.4 NPS と bit 一致

- NPS は CPU 時間で、 ABBA の交互実行、 64〜128 周、 PGO 同士で測る。 逐次実行は交絡し (−63% を −5.7% と読んだ)、 壁時計は同居する作業で揺れ、 8 周では +2% は見えない。
- 計測ビルド (診断の define 入り) の得は本番ビルドに移らないことがある。 PGO は非 PGO の得の半分前後を既にやっている。
- 「結果を変えない」変更は、 探索の関門 (`go nodes` の手・nodes・depth・score・pv の全一致、 広めの局面集) と、 新旧 2 経路の検算 (`*_VERIFY`) の両方を通す。
- 詳細は `SPEEDUPS_STORY.md` 2 章と `speedups/M00_measurement.md`。

施策ごとに、 測る前に判定の線 (何局で、 どの値なら採用・棄却か) を書いてから回しました。 途中経過の数字では判断しません。

## 5. 教訓 (失敗から)

1. **1 つの局面集の基準は、 選び方の偏りを含む**。 v9 の対 v4 同ノード 200 局は 38.0% でしたが、 局面集の前半 50 局面で 48.0%、 後半 50 局面で 28.0% でした。 同じ集合の中でもこれだけ違うので、 1 つの局面集・1 つの基準で「改善した」と読むのは危険です。 腕を選ぶのに使った局面集で、 その腕の強さを報告すると、 選んだ分だけ良く見えます (選択の偏り)。 採否を決める局面と、 強さを報告する局面は分けてください。
2. **局面集の並びにも偏りがある**。 中盤の局面集は順序付きで、 先頭の局面ほど挑戦側に有利でした。 途中で止めると、 止めた位置によって結果が偏ります。
3. **途中経過の数字を報告しない**。 26 局で −13.5pt に見えたものが 600 局で −3.0pt でした (3 回踏んだ)。 判定の線か上限局数まで待つ。
4. **基準の局の「未来」で層別しない**。 対応ペアの差を「基準の局の中の最低評価値」などで層別すると、 差が無くても符号と大きさが出ます。
5. **負けた局の評価が甘く見えるのは、 大部分が選択の偏り**。 負ける側は自分の net に好かれる局面へ歩くので、 我々の静的評価が v4 より +68cp 甘く見えたが、 鏡像を取ると相手にも同じ大きさで出た。
6. **器を 2 回測る**。 指標を作ったら、 同じ入力を 2 回測って器が決定的かを先に確かめる。 陽性対照は本番と同じ経路で取る (別の経路の対照は何も検証しない)。
7. **比較条件を揃えてから原因を言う**。 Threads を変えた対局で、 相手のスレッド数も同時に変わっていたのに「SMP が原因」と書きかけた。
8. **測り方の分解能を先に計算する**。 狙う効果量が、 今の局数・周回数で見えるかを測る前に確かめる。
9. **設定は黙って捨てられる**。 範囲外の USI option の値、 設定ファイルの節の書き間違い、 存在しない define。 「その切り替えは本当にその exe に効いているか」をログで確かめる。
10. **誤差を直すと強くなるとは限らない** (2.7)。 量子化の片寄りのような「誤差」が、 探索と組み合わさって役に立っていることがある。
